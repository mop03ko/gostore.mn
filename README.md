# GOStore · Сонголт нэг дор.

Монгол хэлтэй дэлгүүр + 1688 каталогоос захиалах хүсэлт + админ панел. cPanel-д зориулсан PHP 8.2+, SQLite backend; frontend нь HTML/CSS/JavaScript, build шаардахгүй.

Албан ёсны холбоо барих мэйл: [shop@gostore.mn](mailto:shop@gostore.mn).

## Боломжууд

- Хэрэглэгч: имэйлээр бүртгүүлэх/нэвтрэх, нэр/утас/хүргэлтийн хаягаа хадгалах, нууц үг солих, өөр төхөөрөмжөөс өөрийн захиалгуудыг харах. Зочны хуучин хүсэлтийг тухайн хөтчөөс бүртгэлдээ холбож болно.
- Дэлгүүр: ангилал, хайлт, үнийн шүүлтүүр, сагс, хадгалсан бараа.
- Админ: нэвтрэх, хянах самбар, бараа нэмэх/засах/нуух, үнэ ба үлдэгдэл, зураг оруулах (JPEG/PNG/WebP → JPEG).
- Серверт хадгалагдах барааны болон 1688 захиалга; хэрэглэгч овог нэр, холбоо барих утас, тайлбар оруулна.
- Админ хүсэлт шалгах, нийт үнийн санал өгөх, хүргэлтийн төлөв өөрчлөх, дотоод тэмдэглэл хадгалах.
- QPay Merchant V2 адаптер: token cache, invoice, callback-оор төлбөр шалгах. **Production идэвхтэй: QR үүсгэх, давхар invoice хориглох, төлөөгүй callback шалгагдсан. Бодит төлсөн гүйлгээний төгсгөл хүртэлх шалгалт үлдсэн.**
- 1688 / OT Commerce: Монгол нэртэй бараа хайх, 12 бараагаар хуудсалах, үнэ/өнгө/хэмжээ харах, сонгосон SKU-гаар захиалгын хүсэлт үүсгэх. Сервер 6 цаг кэшлэж, IP болон өдрийн API лимит мөрдөнө.
- Админ → Ханш ба карго: юанийн ханш, жингийн алхам/үнэ, эзлэхүүний босго/тариф, үйлчилгээний хувь, Эрээн агуулахын мэдээлэл. Захиалгын тооцоолуур сервер дээр нийт үнийг гаргаж, тухайн үеийн ханш/тарифыг захиалгад хадгална.
- Хүргэлтийн төлөв: Эрээнд хүлээн авах → багцлах → Замын-Үүдээр дамжин Улаанбаатарт ирэх → захиалга бүрээр ангилах → агуулахаас авах / хүргэлтээр гаргах → хүлээлгэн өгөх. Хэрэглэгч өөрийн захиалгаас явцыг харна.
- Бэлэн барааны худалдаа түр зогссон; Хятад захиалга хэвийн. Эрээн агуулахын панел хятад, Улаанбаатарын панел монгол хэлтэй.

## Ажиллуулах

### Агуулах, хэрэглэгчийн ачаа (2026-10-13)

УБ менежерийн «Барааны тойм»: сайтаас үүссэн цуцлагдаагүй нийт захиалга (бүх хугацааны); Эрээнд одоо байгаа erenhot/erenhot_ready; УБ-д одоо байгаа ulaanbaatar_unsorted/ulaanbaatar/ready_pickup/ready_delivery. Карт тус бүр items.qty эсвэл supplier.qty нийлбэр болон захиалгын тоог харуулна. Хайлт, төлөвийн шүүлт, хуудаслалтаас хамаарахгүй; агуулахаас гарсан/дууссан бараа тухайн агуулахын үлдэгдэлд орохгүй. Эрт үеийн захиалгын дэлгэрэнгүй эрхийг нэмэхгүй, зөвхөн УБ эрхэд нийлбэр үзүүлэлт өгнө.

- Эрээнд багц үүсгэхэд GB кодтой QR шошго гарна. Хэвлээд багцын гадна наана. УБ менежер «Багцын QR уншуулах» → утасны арын камераар уншуулаад тухайн багцын захиалгуудыг нээнэ. Камерын эрхгүй үед QR-ийн зураг сонгох эсвэл GB кодыг гараар оруулж болно. QR унших нь зөвхөн багцыг нээнэ; барааг тулгаж, зураг оруулж, хүлээн авалтыг тусад нь батална. GS захиалгын Code 39 шошго болон USB/Bluetooth сканнерын оролт хэвээр.
- XP-420B хэвлэх: багцын «QR шошго хэвлэх · 100×150» нь QR, GB код, чиглэл, захиалга/барааны тоотой нэг 100×150 мм шошго хэвлэнэ. «Жагсаалт хэвлэх · A4» нь тусдаа бүрэлдэхүүн хэвлэнэ. Windows драйверт 100×150 мм, босоо, 100% масштаб, захын зай 0; хөтчийн толгой/хөлийг унтраана. Шошгоны завсар мэдрэгчийг принтер дээр тохируулна. QR дөрвөн модулийн цагаан хүрээтэй, 203 dpi-д бүхэл цэгээр тааруулсан хэмжээтэй. Хэвлэх/дахин хэвлэх нь төлөв өөрчлөхгүй.
- QR нь зөвхөн дотоод GB код агуулна. Багцын мэдээлэлд менежерийн эрхээр хандана. QR үүсгэх/унших сангууд сайтаас өөрөөс нь ачаалж хөтөч дотор ажиллана; камерын дүрсийг серверт илгээхгүй. Цонх хаах, хуудас солих, гарахад камерыг зогсооно. Лиценз, тогтсон хувилбарууд: assets/vendor/QR-NOTICES.txt.
- Хүлээн авсан захиалга «Эрээн агуулахад ирсэн» (erenhot) төлөвтэй байна. QR багц үүсгэхэд энэ төлөв өөрчлөгдөхгүй. Тулгалт, хэмжилтээ дуусгаад «Багцалж дууссан» товч дарвал багц ready, захиалгууд «Улаанбаатар луу гарахад бэлэн» (erenhot_ready) болно.
- Эрээн менежер багц бодитоор гарсныг чеклээд «Агуулахаас илгээсэн» товч дарсны дараа л багц dispatched, захиалгууд «Замын-Үүд рүү явж байна» (erenhot_dispatched) болж, хэрэглэгч бүрт сайтаар мэдэгдэнэ. Илгээх баталгаажуулалт серверт заавал boolean true байна. Давтан үйлдэл давхар мэдэгдэл үүсгэхгүй.
- Бэлэн болгосон багцын бүрэлдэхүүнийг өөрчлөхийн өмнө «Багцыг дахин засах» товч дарна. Захиалгууд Эрээнд ирсэн төлөвт буцаж, скан тулгалтыг шинээр хийнэ. Илгээсэн багцыг буцаан засахгүй. Өмнөх илгээлт, хүлээн авалтын түүхийг өөрчлөхгүй.
- Эрээнд захиалгын нийт жин, савласан урт/өргөн/өндөр, барааны тоог бүртгэнэ. Бүх захиалгыг скан тулгалтаар баталгаажуулж, хэмжилтээ бүртгэсний дараа багцыг илгээхэд бэлэн болгоно. УБ тал тусад нь бүх GS кодыг тулгаж хүлээн авна. Нэг захиалга бүтнээрээ нэг багцад орно.
- Менежер захиалгын дэлгэрэнгүй → «Хүлээн авах зураг» хэсэгт утасны камераар зураг авч эсвэл файл сонгон хадгална. Хөтөч 20 MB хүртэл эх зургийг урт тал нь 1600 px JPEG болгон багасгаж илгээнэ. Эрээнд хүлээн авахад тухайн агуулахын зураг заавал байна. УБ-д багцын захиалга бүрийн УБ зургийг оруулж байж бүх багцын хүлээн авалтыг батална; нэг захиалга зураггүй бол багц бүхэлдээ хэвээр үлдэнэ. Өмнөх хүлээн авалтын түүхийг өөрчлөхгүй.
- 5 MB, 12 MP хүртэл JPEG/PNG/WebP зураг хүлээн авч JPEG болгон дахин боловсруулна. Зураг `data_dir/warehouse-photos` хавтаст хадгалагдах бөгөөд зөвшөөрөгдсөн агуулах эсвэл тухайн захиалгын эзэмшигч л API-аар үзнэ. Нэг захиалгад агуулах тус бүр 12 хүртэл зураг хадгална. Захиалга болон эзэн тодорхойгүй ачааны зөрчилд зураг хавсаргаж болно.
- Дутуу, гэмтсэн, зөрсөн, илүү бараанд зөрчил бүртгэж тайлбартай шийдвэрлэнэ. Нээлттэй зөрчилтэй захиалгыг илгээх, ангилах, хүлээлгэн өгөхийг хаана. УБ агуулахын тавиурын кодоор хайж болно.
- УБ-д ангилж авах/хүргүүлэх хэлбэрийг сонгосны дараа эцсийн тооцоог батална. Карго нь бодит хэмжилт ба анхны саналын хадгалсан тарифаар (саналгүй бол одоогийн тарифаар) тооцогдоно. Бараа, Хятад хүргэлт, үйлчилгээ, УБ хүргэлтийн дүнг менежер шалгана. Өмнө төлсөн нийт дүнг барааны үнэд давхар оруулахгүй.
- Анхны QPay нэхэмжлэлийг өөрчлөхгүй. Зөвхөн эцсийн тооцооны үлдэгдэлд тусдаа нэхэмжлэл үүсгэж, сервер QPay-ээс төлбөрийг шалгана. Timeout гарсан тодорхойгүй нэхэмжлэлийг дахин үүсгэхгүй. Буцаалт шаардсан тооцоог автоматаар батлахгүй; админ QPay-тай тулган шийдвэрлэнэ.
- Төлбөр бүрэн төлөгдөж, нээлттэй зөрчилгүй үед хэрэглэгчид 8 оронтой нэг удаагийн авах код харагдана. Агуулахын менежер кодыг харахгүй, хэрэглэгчээс авсан кодоор баталгаажуулна. Кодын оролдлогыг 15 минутад 10-аар хязгаарлана.
- «Миний ачаа» нь явцын түүх, хэмжилт, зураг, төлбөрийн задаргаа, авах кодыг харуулна. Зургууд Эрээн/Улаанбаатар агуулахаар ялгарч, Улаанбаатарын цагаар бүртгэсэн огноотой харагдана. Зураг дээр дарж томруулна. GB код, бусад захиалга, ажилтны дотоод тайлбар, тавиур хэрэглэгчид харагдахгүй.
- Төлөв, эцсийн тооцоо, төлбөр өөрчлөгдөхөд болон агуулахын зураг нэмэхэд сайтад мэдэгдэл хадгална. Нэвтэрсэн хэрэглэгч өөрийн мэдэгдлийг харж уншсан болгоно; нээлттэй хуудсанд тоог 60 секунд тутам шинэчилнэ. SMS үйлчилгээ холбогдоогүй.
- Өмнө УБ-д ирсэн хэмжилтгүй ачааны анхны хэмжилтийг УБ менежер нөхөж болно. Хоёр агуулахын эрхийг админ → «Агуулахын эрх» хэсгээс тохируулна.

Тусгаарласан тест: `tmp/tooling/node.exe tests/run-logistics.cjs warehouse-batches logistics customers api warehouse logistics-ui`. Локал PHP, Node, Playwright/Chrome, `tmp/admin-preview.json` тестийн админ тохиргоо шаардлагатай. Тест бүр шинэ `tmp/warehouse-test-*` өгөгдлийн сантай, QPay идэвхгүй сервер ажиллуулаад зогсооно. `tests/freight-payment.php`, `tests/qpay-flow.php` нь хуурамч QPay холболт ашиглана; бодит төлбөр үүсгэхгүй.

Үндсэн кодыг `D:\Gostore.mn` хавтаст засаж хадгална. GitHub нь энэ локал төслийн хувилбарын нөөц юм: [mop03ko/gostore.mn](https://github.com/mop03ko/gostore.mn).

Өөрчлөлтөө шалгасны дараа VS Code → Source Control → Commit → Sync Changes ашиглах эсвэл терминалд:

```powershell
git status
git add <өөрчилсөн-файлууд>
git commit -m "Өөрчлөлтийн тайлбар"
git push origin main
```

Save нь локал файлыг хадгална; Commit/Sync Changes нь GitHub руу хувилбарыг илгээнэ.

Эхлээд өөрийн админ эрхийг локал дээр тохируул:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/configure-admin.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/dev.ps1
```

Дэлгүүр: `http://127.0.0.1:3000/` · Админ: `http://127.0.0.1:3000/admin/`.

PHP суулгасан байх ёстой. Энэ workspace-д `tmp/tooling/php` зөөврийн PHP байгаа бол скрипт түүнийг ашиглана. GitHub-д PHP binary оруулаагүй. Өөр төхөөрөмжид PHP 8.2+ болон `pdo_sqlite`, `mbstring`, `curl`, `gd` суулгана. Локал өгөгдөл `tmp/local-data` дотор хадгалагдана. `scripts/dev.ps1` нь `GOSTORE_DISABLE_QPAY=1` тохируулж локал туршилтаас бодит нэхэмжлэл үүсгэхийг хаана.

Зөвхөн харагдац үзэх бол `index.html` шууд нээж болно; PHP backend-гүй үед хуучин хөтөч доторх нооргийн горим ажиллана. Админ болон серверийн захиалга ажиллахгүй.

## Туршилт

Бүх 21 тестийн багц болон PHP/JavaScript syntax шалгалтыг нэг командаар ажиллуулна:

```powershell
./tmp/tooling/node.exe tests/run-all.cjs
```

Одоогийн Windows орчинд `tmp/tooling/php/php.exe` (pdo_sqlite, mbstring, curl, gd), `tmp/tooling/node.exe`, Playwright болон Chrome шаардлагатай. Тестийн админы эрхийг Git-д орохгүй `tmp/admin-preview.json`-оос уншина. Сервер бүр `tmp/warehouse-test-*` тусгаарласан өгөгдөл ашиглана. QPay идэвхгүй; нийлүүлэгчийн сүлжээний дуудлагыг `GOSTORE_DISABLE_SUPPLIER_NETWORK=1`-ээр хааж, хиймэл каталогийн cache ашиглана. OT UI болон төлбөрийн тестүүд хиймэл хариутай. Live захиалга, бодит төлбөр үүсгэхгүй.

2026-10-13-ны кодын шалгалтаар зэрэг ирсэн давтан хүсэлт, сагсны мөрүүдийн нийлбэр үлдэгдэл, буруу бүтэцтэй сагс, хэт өргөн зураг, буруу нууц үгийн оролт, session дууссаны дараах админ нэвтрэлт, амжилттай илгээсэн сагсыг цэвэрлэх нөхцөлүүдэд регрессийн тест нэмсэн. Live HTTPS шилжүүлэлтийг Apache дээр тусад нь шалгана; PHP хөгжүүлэлтийн router `.htaccess` дүрэм ажиллуулдаггүй.

Loopback дээр тусгаарласан тестийн сервер ажиллуулж `tests/api.mjs` (Node 22+) болон `php tests/qpay.php` шалгалтыг гүйцэтгэсэн. API тест нь түр админ тохиргооны `tmp/admin-preview.json` файлыг ашигладаг; өөрийн production сервер рүү тест явуулахгүй. Бэлэн барааг хамарсан өмнөх `tests/api.mjs`, `tests/customers.mjs` тестийг ажиллуулах серверт `GOSTORE_LOCAL_PRODUCTS_ENABLED=1` тохируулна.

Шалгасан: нэвтрэх/гарах, зөвшөөрөлгүй API, CSRF, private файлын хамгаалалт, бараа хадгалалт ба нуух, зураг шалгах/хөрвүүлэх, серверээс үнэ тооцох, давхар хүсэлтээс сэргийлэх, захиалгын эзэмшлийн түлхүүр, үнийн санал, QPay идэвхгүй горим, төлбөрийн currency/status/amount болон duplicate ID, хуурамч нийлүүлэгчийн холбоос.

## Хязгаар

Production seed болон frontend fallback хоосон; тестийн жишээ бараа зөвхөн `tests/catalog-fixture.json`-д байна. `demo_catalog_removed_v1` нэг удаагийн migration нь demo=true барааг soft-delete хийж, бодит болгож зассан бараа болон захиалгын түүхийг хадгална.
- Үлдэгдэл нь нийт барааны лавлах тоо; хувилбар тус бүрийн reservation болон автоматаар хасах урсгал одоогоор байхгүй.
- Үндсэн админ, Эрээн болон Улаанбаатарын тус бүр нэг менежерийн эрхтэй. Нэг агуулахад олон ажилтны тусдаа бүртгэл, refund, eBarimt, нийлүүлэгчид автоматаар худалдан авах болон каргоны гадаад API хэрэгжээгүй. 1688 каталог нь бүх барааг нэг дор хуулдаггүй; хэрэглэгчийн хайлтаар API-аас авна.
- Админ сүүлийн 1000 хүсэлтийг харуулна. Захиалга харах түлхүүр хэрэглэгчийн хөтөчид хадгалагдана.
- QPay идэвхтэй; бодит төлсөн гүйлгээний acceptance шалгалт үлдсэн. 1688 хүсэлтийн үнэ/үлдэгдэл/Хятад хүргэлтийг админ баталгаажуулж байж QPay санал гаргана.

## 1688 захиалга ба карго

### Эрээн болон Улаанбаатар агуулахын панел

1. Үндсэн админ `/admin/` → **Агуулахын эрх** хэсэгт Эрээн, Улаанбаатарын менежер бүрийн имэйл, 12–72 байтын нууц үгийг тус тусын маягтад оруулж, **Менежерийн эрх идэвхтэй** сонголтыг идэвхжүүлэн хадгална.
2. Эрээн: `/warehouse/?location=erenhot` (хятад хэл). Улаанбаатар: `/warehouse/?location=ulaanbaatar` (монгол хэл). Захиалгыг код, хүлээн авагч, барааны нэрээр; багцыг GB код, тэмдэглэлээр хайна. Жагсаалт 50 бүртгэлээр хуудсална.
3. Эрээн менежер баталгаажсан/Эрээн рүү хүргэлтэд буй захиалгын бараа, хувилбар, тоог тулгаж хүлээн авна. Ирсэн захиалгуудаас сонгон эсвэл GS кодыг оруулан **创建包裹** үйлдлээр багц үүсгэнэ. Нэг захиалга бүтнээрээ зөвхөн нэг багцад орно; багцад 200 хүртэл захиалга бүртгэнэ.
4. Багц `GB-` + 6 тэмдэгт кодтой (жишээ: `GB-A1B2C3`). Илгээгээгүй багцад захиалга нэмэх, хасах, багцыг цуцлах боломжтой. Шошго болон бүрэлдэхүүнийг хэвлэж болно. **确认发运** үйлдлээр бүх захиалга хамт илгээгдэж, бүрэлдэхүүн түгжигдэнэ. Маршрут: Эрээн → Замын-Үүд → Улаанбаатар.
5. Улаанбаатар менежер багцын кодоор хайж **Багц ирснийг хүлээн авах** үйлдэл хийнэ. Бүх захиалга «Багцаар ирсэн · ангилаагүй» болно. Багцыг задлаад захиалга тус бүрийн бараа, хувилбар, тоог тулгаж, утас болон авах хэлбэрийг баталгаажуулна. Бүх захиалгыг ангилсны дараа багц «Бүгдийг ангилсан» болно.
6. **Агуулахаас авах** захиалгыг хэрэглэгчид өгөөд бодитоор хүлээн авсан хүний нэрээр баталгаажуулна. **Хүргэлтээр авах** захиалгад бүрэн хаяг шаардлагатай; хүргэгчийн нэр, утсаар хүргэлтэд гаргаж, дараа нь хүлээлгэн өгснийг батална. Авах хэлбэрийг гаргахаас өмнө өөрчилж болно. Эдгээр үйлдэл үнэ, төлсөн дүнг өөрчлөхгүй.
7. Багцтай болон ангилсан захиалгын төлөвийг үндсэн админы ерөнхий засвар тойрч өөрчилж болохгүй. Өмнөх багцгүй захиалгуудад админ Замын-Үүдэд ирснийг тэмдэглэж, Улаанбаатар менежер хүлээн аваад ангилах хуучин урсгал хэвээр ажиллана.

Менежерүүд барааны бүрэлдэхүүн, агуулахын шошго, хүргэлтийн явцыг харна. Улаанбаатар менежерт бараа ирсний дараа хүлээлгэн өгөхөд хэрэгтэй утас, хаягийг харуулна; Эрээн панел эдгээрийг авахгүй. Үнэ, төлбөр, дотоод тэмдэглэл, нууц түлхүүрийг аль ч менежерийн API өгөхгүй. Багцын GB код нь агуулахуудын дотоод тээврийн бүртгэлд ашиглагдана. Хэрэглэгч өөрийн анхны GS захиалгын кодоор явц, авах хэлбэр, төлөвийг харна; багцын код, бусад захиалгын жагсаалт, хүргэгчийн мэдээлэл, ажилтны имэйл хэрэглэгчийн API болон дэлгэцэд харагдахгүй. Үйлдлийн түүхэнд ажилтны имэйл, агуулах, огноог сервер хадгална.

Эрх хаах, имэйл/нууц үг өөрчлөх эсвэл дахин хадгалахад зөвхөн тухайн агуулахын хуучин session хүчингүй болно. Нөгөө агуулахын эрх хэвээр үлдэнэ. Өмнөх Эрээн агуулахын нэвтрэх эрх хадгалагдана. Анхны нууц үг болон идэвхтэй эрх урьдчилан үүсгэхгүй. Багцын хүснэгтүүд анхны хүсэлтээр өгөгдлийн санд автоматаар үүснэ; өмнөх захиалгыг дахин үүсгэх шаардлагагүй.

Бэлэн барааны бүртгэл ба өмнөх захиалгууд хадгалагдана. Буцааж нээх бол серверийн `config.local.php` дотор `'local_products_enabled' => true` тохируулна. Хаалттай үед public каталог, хөтчийн сагс, шинэ захиалгын API бэлэн барааг зөвшөөрөхгүй. Үндсэн админ барааны бүртгэлийг үргэлжлүүлэн удирдана.

Агуулахын тест: `GOSTORE_DATA_DIR`-г `tmp/warehouse-test-<unique>` тусгаарласан хавтас, `GOSTORE_DISABLE_QPAY=1`, `GOSTORE_DISABLE_SUPPLIER_NETWORK=1` болгож, `GOSTORE_LOCAL_PRODUCTS_ENABLED`-г тохируулахгүй. `php tests/warehouse-fixtures.php` дараа localhost сервер ажиллуулаад `TEST_BASE=http://127.0.0.1:<port>`-той `node tests/warehouse.mjs` гүйцэтгэнэ. Багц, эрх, атомик шинэчлэлт, хувийн мэдээлэл, ангилалт/хүргэлтийн тестийг **өөр шинэ fixtures ба өгөгдөлтэй сервер** дээр `node tests/warehouse-batches.mjs` командаар ажиллуулна. Түр админы hash нь `tmp/admin-preview.json` дахь тестийн эрхтэй таарах ёстой. Fixtures нь бодит захиалгын өгөгдөлд зориулсан биш.

Сайт → **Хятадаас захиалах** хэсэгт нэрээр хайж, барааны өнгө/хэмжээ, тоо ширхэгээ сонгоод хүсэлт илгээнэ. Нийлүүлэгчийн үнэ нь юань; төгрөгийн үнэ хүргэлтгүй лавлах дүн. Багцын хөнгөлөлт, хувилбарын үнэ, үлдэгдэл болон Хятад доторх хүргэлтийг оператор нягтална. Энэ холболт нийлүүлэгчид төлбөр хийж автоматаар худалдан авдаггүй.

**Админ → Ханш ба карго** хэсэгт эхний тохиргоо:

- 1¥ = 550₮; үйлчилгээний шимтгэл 0% (засаж болно).
- Жин: `ceil(нийт кг / 0.5) × 1500₮`.
- Эзлэхүүн: 1 м³-ээс бага үед `м³ × 599¥ × ханш`; 1 м³ ба түүнээс их үед `м³ × 399¥ × ханш`.
- Жин ба эзлэхүүний аргыг админ захиалга бүр дээр сонгоно; автоматаар нийлүүлж эсвэл ихийг нь авдаггүй.
- Эрээн агуулах: `内蒙古锡林郭勒盟二连浩特市环宇商贸城10-16号`; Хятад утас `18047981132`, нэмэлт утас `99889815`. Админ шаардлагатай үед шинэчилж болно.

**Захиалга → Харах → Ханш, каргоор үнийн санал тооцох** хэсэгт барааны нийт CNY, Хятад хүргэлтийн CNY, нийт жин эсвэл эзлэхүүнийг оруулна. Тооцоод нийт саналд оруулж, төлөвийг **Үнийн саналтай** болгон хадгална. QPay нэхэмжлэл үүссэн бол дүн, тооцоог засахгүй. Ханш/тарифын өөрчлөлт өмнөх захиалгын үнийн саналыг өөрчлөхгүй. Багцын тээвэр, ангилалт, хүлээлгэн өгөх төлөвийг дээрх агуулахын панелаас удирдана.

OT Commerce API нь [албан ёсны REST баримтжуулалт](https://apidoc.otapi.net/)-ын `alibaba1688/search` болон `alibaba1688/product/{id}` маршрутыг ашиглана. Нууц түлхүүр зөвхөн серверт байна. Бүх 1688 каталогийг бүрэн татахгүй; хайлт бүр 12 бараагаар хуудсалж, 6 цаг серверт хадгална. Кэш шинэчилж чадахгүй үед хадгалсан мэдээлэл гэсэн тэмдэглэгээтэй харуулж, хуучирсан мэдээллээр шинэ захиалга баталгаажуулахгүй. Эхний лимит 40 шинэ API дуудлага/UTC өдөр, 10/IP/цаг; админ өдрийн хязгаарыг засаж болно. Энэ нь OT Commerce-ийн үлдсэн дуудлагын тоо биш. Trial эрх дуусвал үйлчилгээ үзүүлэгч дээр сунгана.

`php tests/shipping.php`: карго тоймлолт, 1 м³ босго, буруу тоо, CNY валют ба SKU хөрвүүлэлтийг шалгана. `tests/supplier.mjs`: тусгаарласан localhost сервер, түр админ эрх болон "bag" хайлт/эхний барааны кэштэй үед ажиллана. `GOSTORE_DISABLE_SUPPLIER_NETWORK=1` нь локал тестээр бодит API дуудлага гаргахаас сэргийлнэ. Кэшний файл, нийлүүлэгчийн бүтэн response, нууц тохиргоог Git-д оруулахгүй.

## Эрээн агуулахын хүлээн авагч

Линк оруулж захиалах форм, цэс, fallback болон API шинэ захиалга хаагдсан. Захиалгын эх үүсвэр нь дэлгүүрийн каталог эсвэл 1688 SKU байна. Хуучин линк хүсэлтийн түүх устахгүй.

Шинэ Хятад захиалгад овог, нэр заавал өгнө. Сервер захиалгын өөрийн GS кодоор `Овог Нэр / GS-…` хүлээн авагч үүсгэж, хаяг/утсыг тухайн захиалгад хадгална. Дараа нь агуулахын тохиргоо эсвэл профайлын нэр солигдоход өмнөх шошго өөрчлөгдөхгүй.

Админ → Захиалгууд → Харах → **Хаяг, овог нэр, код хуулах**. Оператор энэ мэдээллийг нийлүүлэгчийн хүргэлтийн хаягт оруулж, илгээмжийн шошгод овог нэр ба GS кодыг заавал бичүүлнэ. Энэ шинэчлэл нийлүүлэгчийн худалдан авалтын API-г автоматаар дуудахгүй. Хэрэглэгч өөрийн захиалгын дэлгэрэнгүйгээс мөн хүлээн авагчийн мэдээллийг харна.

## Super админ, бараа, агуулахын тохиргоо

- **Нууц үг солих**: одоогийн нууц үг, шинэ нууц үг, давталтаа оруулна. 12+ тэмдэгт, bcrypt-ийн 72 байтын хязгаартай. Сервер зөвхөн hash хадгална; бусад төхөөрөмжийн админ session хүчингүй болж, одоогийн session болон CSRF шинэчлэгдэнэ.
- **Бараа бүтээгдэхүүн → Засах / Устгах**: нэр, зураг, үнэ, үлдэгдэл, хувилбарууд, нийтлэх төлөвийг засна. Устгах үед баталгаажуулах checkbox шаардлагатай. Устгасан бараа каталог болон админы жагсаалтаас хасагдаж, хуучин засварын хүсэлтээр сэргээгдэхгүй. Өмнөх захиалгын барааны нэр, үнэ хэвээр үлдэнэ; серверт устгасан тэмдэглэгээтэй бүртгэл хадгалагдана.
- **Агуулахууд**: Эрээн, Улаанбаатарын нэр, хаяг, үндсэн/нэмэлт утас, ажиллах цаг болон менежерийн эрхийг тус тусад нь засна. Эрээний шинэ хаяг шинэ захиалгад хэрэглэгдэнэ; өмнөх шошго хэвээр байна. Улаанбаатарын одоогийн мэдээлэл агуулахаас авах захиалгын дэлгэрэнгүйд харагдана. Ханш хадгалах нь агуулахын мэдээллийг арилгахгүй.

Админ нууц үгээ анх сольсноос хойш DB-ийн `meta.admin_password_hash` нь `config.local.php` дахь анхны hash-аас давуу эрхтэй. Анхны тохиргооны скрипт нь нууц үг сэргээх хэрэгсэл биш. Серверийн эрхтэй оператор сэргээх шаардлагатай бол хувийн DB-д шинэ bcrypt hash тавина; хуучин plaintext нууц үг хадгалагдахгүй. Шинэ хувилбарын өмнөх админ session-ууд дахин нэвтрэх шаардлагатай.

Локал, тусгаарласан тестүүд: `node tests/run-logistics.cjs admin-management admin-management-ui` (Chrome UI, бусад session хаагдах, хуучин нууц үг хүчингүй болох, агуулах тусгаарлалт, захиалгын snapshot болон бараа устгал). Live нууц үг, бараа, агуулахын мэдээллийг тестээр өөрчлөхгүй.

## OT операторын холболт

Үндсэн админ → **API холболтууд → 1688 худалдан авалтын холболт** хэсэгт OT Commerce-оос өгсөн операторын нэр, нууц үгээр нэвтэрнэ. Энэ нь GOStore админы нууц үгээс тусдаа эрх юм. Нууц үгийг хадгалахгүй; OT session зөвхөн public_html-ээс гаднах серверийн өгөгдлийн санд хадгалагдана. Session хүчингүй бол дахин нэвтэрнэ.

**Холболт шалгах** товч Business Logic, Alibaba1688 Autopurchase болон худалдан авагчийн холбосон аккаунтын тоог шалгана. **1688 аккаунт холбох** товч OT-оос ирсэн HTTPS нэвтрэх холбоосыг харуулна. Нэвтрэлтээ дуусгаад GOStore админд буцаж **Холболт шалгах** товчийг дахин дарна. GOStore холболт салгах нь локал OT session-ийг устгана; 1688 талын зөвшөөрлийг цуцлахгүй.

Энэ хувилбар холболт тохируулах зориулалттай. Нийлүүлэгчид бодит захиалга үүсгэх, мөнгө төлөх үйлдэл нэмэгдээгүй. Холболтын API зөвхөн нэвтрэлт болон унших аргуудын жагсаалтыг зөвшөөрнө. Түлхүүрийн `secret` шаарддаг signed OTAPI тохиргоо энэ хувилбарт ороогүй.

Албан ёсны баримт: [операторын нэвтрэлт](https://docs.otapi.net/en/Documentations/Method/AuthenticateInstanceOperator), [1688 нэвтрэх холбоос](https://docs.otapi.net/en/Documentations/Method/GetProviderOrdersIntegrationSessionAuthenticationInfo), [холбосон аккаунтууд](https://docs.otapi.net/en/Documentations/Method/GetProviderOrdersIntegrationSessionInfoList). Response бүтэц нь албан ёсны `SessionIdAnswer`, `ProviderAuthenticationInfoAnswer`, `ProviderSessionInfoListAnswer` JSON жишээнд тулгуурласан.

Нэвтрэх алдаа OT-ийн `GeneralErrorCode`-оор ялгагдана (`LoginFailed`, `AccessDenied`, `IncorrectKey` гэх мэт). Админд сүүлийн зөвшөөрөгдсөн алдааны код, арга, цагийг харуулна. Provider-ийн raw response, ErrorDescription, password, session болон request ID-г оношилгоонд хадгалахгүй. Нэвтрэлт эсвэл холболт шалгах амжилттай бол өмнөх алдаа арилна.

Тест: `tests/ot-operator.php` fake OT transport ашигладаг; `node tests/run-logistics.cjs ot-operator` нь зөвхөн локал серверт админ/CSRF хамгаалалтыг шалгана. Эдгээр тест OT руу хүсэлт болон бодит захиалга илгээхгүй.

GOStore Collection нь 1688 API хайлтын нэг каталог болсон. Үндсэн хайлт, ангилал, эрэмбэ, хуудаслалт API үр дүнг харуулж, барааг /v/{id} хуудсаар нээнэ. Хуучин дотоод каталог болон жишээ барааг Collection-д дүрслэхгүй. API алдахад дахин оролдох төлөв харуулна. Хадгалсан 1688 бараа тусдаа хөтчийн санд хадгалагдаж, дэлгэрэнгүй хуудсанд үнэ/үлдэгдлийг дахин шалгана.

Хэрэглэгчийн UX шинэчлэлт: mobile цэсээс хадгалсан бараа/ачаагаа шууд нээнэ; хайлтын q/sort/page/filter URL-д хадгалагдана; ачаалалтын skeleton, хоосон үр дүн ба цэвэрлэх товчтой. Барааны зураг нэг харьцаатай, нэр хоёр мөрөөр харагдана. Захиалгын мэдээлэл оруулахад сонгосон барааны зураг, дараалал харагдана. Ачааны таван шат нь бодит төлөвийг дагаж, Эрээнд багцалсныг замд гарсантай андуурахгүй. Цуцлагдсан ачааг тусад нь шүүж, үнийн санал ирсэн, төлөгдөөгүй захиалгыг төлбөрийн бүлэгт харуулна. Огноо Улаанбаатарын цагаар YYYY.MM.DD · HH:mm форматтай.

Барааны cache: серверийн OT хариу 6 цаг хадгалагдана. Хөтчийн sessionStorage-д хайлт (q/page/sort тус бүр) 10 минут, дэлгэрэнгүй 5 минут хадгалж, серверийн үлдсэн хугацаагаар хязгаарлана. Нэг tab-д 40 хүртэл хариу, ойролцоогоор 1.5 MB багтаамжтай; хуучин бичлэгүүд эхэлж хасагдана. Давхардсан зэрэгцээ хүсэлтийг нэгтгэнэ. Хуудас дахин нээхэд cache-аас шууд харуулж, cache дууссан үед шинэ хүсэлт явуулна. Алдаа, stale хариу, хэрэглэгч/CSRF/төлбөр/захиалгыг хадгалахгүй. Storage боломжгүй үед memory cache ажиллана. Захиалга илгээхэд session бэлэн болсны дараа сервер үнэ, SKU, үлдэгдлийг дахин шалгана; харагдаж буй үнэ эцсийн төлбөр биш.

Cache шалгалт: `node tests/run-logistics.cjs supplier supplier-cache-ui collection-ui product-page-ui`. Локал fixture ашиглаж, OT API болон бодит төлбөр зарцуулахгүй.
